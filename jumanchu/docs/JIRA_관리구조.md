# 주만추 Jira 관리 구조 가이드

> 대상: 주만추(Django + Vue.js) 2–3인 SSAFY 스크럼 팀
> 목적: 모두가 같은 규칙으로 이슈를 만들고, 상태를 옮기고, 마무리하기

---

## 1. 이슈 위계 (Issue Hierarchy)

```
Epic        : 큰 기능 단위 / 마일스톤 (1~3 스프린트에 걸침)
 └─ Story   : 사용자 가치 단위 ("나는 ~로서 ~를 하고 싶다", 1~3일)
     └─ Sub-task : Story를 쪼갠 작업 단위 (반나절~1일)
 └─ Task    : 사용자 가치는 없지만 필요한 작업 (세팅, 리서치, 문서)
 └─ Bug     : 동작이 의도와 다른 결함
```

### 1.1 어떤 타입을 쓸까

| 상황 | 타입 |
|---|---|
| "포트폴리오 공유 커뮤니티" 같은 큰 기능 묶음 | **Epic** |
| "회원가입 화면에서 이메일/비밀번호로 가입한다" | **Story** |
| Story를 FE/BE/DB로 나눈 실제 작업 | **Sub-task** |
| 프로젝트 초기 세팅, ERD 작성, API 키 발급 | **Task** |
| 이미 만든 기능이 동작하지 않음 | **Bug** |

### 1.2 입도(粒度) 규칙

- **Epic**: 한 줄로 사용자 가치 설명 가능해야 함. 보통 5~15개의 Story 포함.
- **Story**: 1인이 **1~3일** 안에 끝낼 수 있는 단위. 그보다 크면 쪼갠다.
- **Sub-task**: **반나절~1일**. PR 하나에 대응되는 정도.
- **Bug**: 재현 절차 + 기대 결과 + 실제 결과가 항상 본문에 있어야 함.

### 1.3 명명 규칙

- **Epic**: `[도메인] 큰 기능 이름` 예) `[종목추천] 트렌딩 뉴스 기반 추천`
- **Story**: 사용자 관점 한 문장. 예) `사용자가 관심 종목을 스와이프로 등록한다`
- **Task**: 동사로 시작. 예) `DART API 키 발급 및 환경변수 설정`
- **Bug**: `[Bug] 증상 한 줄 요약`. 예) `[Bug] 로그아웃 후에도 포트폴리오 페이지 접근 가능`

## 2. 워크플로우 (Workflow)

### 2.1 상태 전이

```
 ┌────────┐   start    ┌─────────────┐   PR open   ┌───────────┐   merge   ┌──────┐
 │ To Do  │ ─────────▶ │ In Progress │ ──────────▶ │ In Review │ ────────▶ │ Done │
 └────────┘            └─────────────┘             └───────────┘           └──────┘
     ▲                       │   block                  │ change request        │
     │                       ▼                          ▼                       │
     │                  ┌─────────┐                ┌─────────────┐              │
     └──────────────────│ Blocked │                │ In Progress │◀─────────────┘
              reopen    └─────────┘                └─────────────┘   bug found
```

### 2.2 상태별 의미와 책임

| 상태 | 의미 | 진입 조건 | 담당자 책임 |
|---|---|---|---|
| **To Do** | 스프린트에 들어왔지만 시작 전 | 스프린트 시작 | 담당자(Assignee) 지정 필수 |
| **In Progress** | 작업 중 | 담당자가 실제 코드/문서 작업 시작 | **하루 이상 머물면 데일리에서 공유** |
| **In Review** | PR 올라감, 리뷰 대기 | PR 링크가 이슈에 첨부됨 | 리뷰어 지정 필수 |
| **Blocked** | 외부 요인으로 진행 불가 | 사유를 코멘트로 명시 | **24시간 내** 데일리에서 공유 |
| **Done** | 작업 완료, DoD 충족 | DoD 체크리스트 통과 | 담당자가 직접 Done 처리 |

### 2.3 Definition of Ready (DoR) — Story가 In Progress로 가기 전

- [ ] 사용자 가치가 한 문장으로 서술돼 있다
- [ ] 인수 조건(Acceptance Criteria) 3개 이상
- [ ] 담당자가 지정돼 있다
- [ ] Story Point가 추정돼 있다 (1, 2, 3, 5, 8)
- [ ] 의존하는 다른 이슈가 모두 식별돼 있다

### 2.4 Definition of Done (DoD) — Done으로 옮기기 전

- [ ] 인수 조건이 모두 충족됨
- [ ] PR이 머지됨 (Sub-task 제외)
- [ ] 최소 1명의 코드 리뷰 통과
- [ ] 관련 문서/주석 업데이트
- [ ] 로컬 + 개발 서버에서 동작 확인
- [ ] 새 버그가 생겼다면 별도 Bug 이슈로 등록

## 3. 라벨 / 컴포넌트 / 우선순위

### 3.1 컴포넌트 (Components) — *기술 영역*

| 컴포넌트 | 범위 |
|---|---|
| `backend` | Django, REST API, 모델, 마이그레이션 |
| `frontend` | Vue.js, 컴포넌트, 라우팅, 상태관리 |
| `infra` | 배포, CI/CD, 환경변수, 도커 |
| `design` | UI/UX, 화면 시안, 디자인 시스템 |
| `docs` | README, 명세서, 회의록, WBS |

> 한 이슈는 보통 컴포넌트 1개. FE+BE가 함께 필요하면 Story 하나에 Sub-task로 쪼개되, Sub-task별 컴포넌트는 단일 지정.

### 3.2 라벨 (Labels) — *도메인/맥락*

도메인 라벨 (소문자, kebab-case):

- `auth` — 회원가입/로그인/온보딩
- `stock-data` — 종목 조회, 주가, 시장 요약
- `portfolio` — 보유 종목, 포트폴리오 현황
- `recommend` — 추천 알고리즘, 스와이프 UI, 투자 MBTI
- `community` — 게시판, 댓글, 리뷰
- `news` — 트렌딩 뉴스, 스크랩
- `finance-report` — DART, 재무제표
- `diary` — 매수/매도 일기, 회고

운영 라벨:

- `tech-debt` — 리팩토링, 코드 정리
- `spike` — 기술 조사/리서치 (타임박싱: 1일)
- `blocked-external` — 외부 API/서비스 때문에 막힘
- `good-first` — 새로 합류한 사람이 잡기 좋은 작업

### 3.3 우선순위 (Priority)

| 우선순위 | 기준 | 예시 |
|---|---|---|
| **P0 / Highest** | 데모/시연 직전, 동작 안 하면 발표 불가 | 로그인 안 됨 (시연 D-1) |
| **P1 / High** | 이번 스프린트 안에 반드시 끝나야 함 | 핵심 사용자 흐름 |
| **P2 / Medium** | 이번 스프린트 목표지만 다음 스프린트로 밀려도 됨 | 부가 기능 |
| **P3 / Low** | 있으면 좋지만 없어도 됨 | UI 폴리싱, 문구 다듬기 |

> P0는 **동시에 2개를 넘지 않는다**. 모든 게 P0면 아무것도 P0가 아니다.

## 4. 스프린트 / 백로그 운영

### 4.1 스프린트

- **길이**: 1주 (월요일 시작 → 금요일 종료, 데모 포함)
- **스프린트 플래닝**: 월요일 오전 (Story Point 합계 = 팀 속도 기준)
- **데일리 스크럼**: 매일 10분 — 어제 한 일 / 오늘 할 일 / 블로커
- **스프린트 리뷰 + 회고**: 금요일 오후

### 4.2 Story Point (참고)

- `1` — 자명, 30분 내. 문구 수정 수준
- `2` — 반나절, 단일 컴포넌트 수정
- `3` — 하루, 새 화면/엔드포인트 1개
- `5` — 2~3일, 외부 API 연동 또는 여러 화면 연관
- `8` — 1주 가까이, Story를 더 쪼개야 한다는 신호

### 4.3 백로그 그루밍

- 매주 수요일 30분: 다음 스프린트 후보 Story들의 DoR 점검
- Story 한 줄 설명 + 인수 조건 + 추정 SP를 채워둔다

## 6. 샘플 Story 템플릿

```
제목: 사용자가 이메일과 비밀번호로 회원가입한다

설명:
나는 신규 사용자로서, 이메일과 비밀번호로 가입하여
주만추 서비스를 시작하고 싶다.

인수 조건:
- [ ] 이메일 형식 검증이 실패하면 에러 메시지가 보인다
- [ ] 비밀번호는 8자 이상 + 영문/숫자 조합이어야 한다
- [ ] 가입 성공 시 온보딩 화면으로 이동한다
- [ ] 이미 가입된 이메일이면 안내 메시지가 보인다

기술 메모:
- BE: POST /api/v1/auth/signup
- FE: SignupView.vue, Pinia auth store

Epic: [인증] 회원가입 / 로그인 / 온보딩
Components: backend, frontend
Labels: auth
Priority: P1
Story Point: 3
```

## 7. 샘플 Bug 템플릿

```
제목: [Bug] 로그아웃 후에도 포트폴리오 페이지에 접근 가능

재현 절차:
1. 로그인한다
2. /portfolio 진입 후 정상 동작 확인
3. 헤더에서 로그아웃 클릭
4. 주소창에 /portfolio 직접 입력

기대 결과: /login 으로 리다이렉트 되어야 함
실제 결과: 캐시된 포트폴리오 화면이 그대로 보임

환경: Chrome 124, 개발 서버
Priority: P1
Components: frontend
Labels: auth
```

## 8. 운영 체크포인트 (한눈에)

- 새 이슈를 만들 때 **타입 / 컴포넌트 / 라벨 / 우선순위 / 담당자 / SP**를 반드시 채운다
- Story는 **사용자 관점** 한 문장으로 시작한다
- "내가 지금 하고 있는 일"이 보드에 **In Progress**로 떠 있어야 한다
- Blocked는 24시간 안에 공유한다
- Done은 DoD 체크리스트를 통과해야 한다
- P0는 동시에 2개를 넘기지 않는다
