# 추천·장투 DB 결정서 — 정율 완벽안 → 데모 타협안

- 작성일: 2026-06-07
- 작성: 강재민 (BE)
- 목적: 정율이 설계한 **완벽안**([`ALGORITHM_DB_OPTIMIZATION_SPEC.jy.md`](./ALGORITHM_DB_OPTIMIZATION_SPEC.jy.md))을, 6주 데모 현실에 맞게 줄인 **타협안**과 나란히 비교하고, 우리가 실제로 구현할 최종안을 확정한다.

---

## 0. 두 안이 무엇인가

**정율 완벽안 (2026-05-31)**
추천(궁합)과 장투 알고리즘을 *끝까지 다 구현했을 때*를 가정한 풀 스펙 DB 설계다. 신규 테이블 9개에 더해 사용자 행동 로그(파티셔닝), 행동 학습 집계, 종목 장투 종합점수, 섹터 평균 MV, 커넥션 풀링, 배치 스케줄까지 운영·확장을 모두 대비해 두었다. "이상적인 완성형"이라 보면 된다.

**우리 타협안 (2026-06-07, 본 문서)**
6주 프로젝트 + 발표(6/25)라는 현실에서, *데모에 실제로 보여줄 것*만 남기고 나머지는 "확장 가능성"으로 미룬 실전 최소안이다. 동시에, 완벽안이 **비워두었던 점수 산식**(정규화 방식·뉴스/기술 점수·종합점수 합산 가중치 등)을 우리가 구체적인 숫자로 채웠다.

한 줄로: **정율안에서 "데이터가 쌓여야 의미 있는 학습" + "범위 밖 기능" + "운영 최적화"를 걷어내고, 대신 비어 있던 산식을 채운 것**이 우리안이다.

## 0-1. 용어 사전 (이 문서에 나오는 말들)

| 용어 | 쉽게 말하면 | 우리 프로젝트 예 |
|---|---|---|
| **온더플라이 (on-the-fly)** | 미리 저장 안 하고, 필요한 순간에 즉석에서 계산. (주문 받고 그때 요리하기) | `stock_dna`를 미리 만들어 저장하는 대신, 추천 요청 올 때 그 자리에서 계산 |
| **캐시 (cache)** | 매번 다시 계산하기 아까운 결과를 미리 만들어 저장해두는 것. (반찬 미리 만들어 냉장고에) | `stock_dna`, `recommendation_cache` |
| **defer (디퍼)** | 지금 말고 나중으로 미루기 | 뉴스 감성점수 컬럼은 뉴스 기능 붙일 때 추가, 그전엔 50점 고정 |
| **확장 (extension)** | 지금 핵심엔 안 넣고 나중에 덧붙일 기능. 발표 땐 "이것도 가능"으로만 소개 | 행동학습 |
| **정규화 (normalize)** | 단위가 제각각인 값들을 0~1처럼 같은 잣대로 맞추는 것 | PBR·EPS·beta를 0~1 점수로 변환 |
| **백분위 (percentile)** | 전체 중 몇 %에 위치하는지로 점수 매기기. (반 등수처럼) | 정규화 방식으로 채택 |
| **배치 (batch)** | 실시간이 아니라 정해진 시간에 한꺼번에 처리하는 작업. (밤마다 한 번 돌리기) | 매일 밤 종목 점수 계산 |
| **마이그레이션 (migration)** | 모델(테이블) 변경사항을 DB에 실제로 반영하는 Django 작업 | `makemigrations` → `migrate` |
| **FK (외래키)** | 한 테이블이 다른 테이블을 가리키는 연결. (이 행은 어느 유저 것인지) | `user_liked_stock.user_id` → `accounts_user` |
| **스냅샷 (snapshot)** | 어떤 순간의 값을 사진 찍듯 그대로 박제해 저장 | Like 누른 시점의 PBR을 `base_pbr`에 저장 |
| **TTL (Time To Live)** | 저장한 데이터의 유효기간. 지나면 버림 | 추천 캐시는 하루 뒤 만료 |
| **파티셔닝 (partitioning)** | 큰 테이블을 날짜 등으로 잘게 나눠 저장. (월별 서랍) | 행동 로그(우리안에선 제외) |
| **MV (Materialized View)** | 자주 쓰는 집계 결과를 미리 계산해 저장해두는 특수 뷰 | 섹터 평균(우리안에선 선택) |

## 1. 타협의 세 가지 기준

우리가 무언가를 뺐다면, 아래 셋 중 하나에 해당한다.

1. **데이터 누적이 있어야 작동하는 기능** — 데모는 신규 유저뿐이라 행동 데이터가 비어 있다. 통계·학습 기능은 시연해도 결과가 빈약하다. → *행동 학습* 제외.
2. **이번 범위에서 빠진 기능** — 팀이 포트폴리오 공유 기능을 데모에서 빼기로 했다. → *SharedPortfolio* 제외.
3. **운영 최적화 (지금은 불필요)** — 동시 사용자가 적은 데모에선 파티셔닝·pgBouncer·MV 튜닝이 체감 이득이 없다. → *발표 "확장 가능성"에 언급만*.

반대로, 완벽안이 **모호하게 남겨둔 산식**은 그대로 두면 구현이 막히므로, 우리가 데모용 기본값으로 **확정**했다.

## 2. 테이블별 상세 비교

### 2-1. `accounts_investmentprofile` (기존 테이블 → 컬럼 추가)
- **완벽안**: 5차원 성향 벡터(risk_tolerance/investment_term/experience/loss_aversion/behavior) + 투자금액 범위 + 목표수익률 + 리스크 허용폭 + 온보딩 8문항 원답(JSON)을 전부 추가.
- **우리안**: 5벡터 + `onboarding_answers` + `profiled_at`은 **필수**로 추가한다(궁합 알고리즘의 입력이라 없으면 추천 자체가 안 된다). 투자금액·목표수익률·리스크폭은 궁합 점수 공식에 직접 쓰이지 않고 "예산 초과 종목 거르기(콜드스타트 필터)"에만 쓰이므로 **선택**으로 둔다. 데모에 예산 필터를 안 넣으면 생략해도 된다.
- **이유**: 5벡터는 추천의 심장이라 무조건 필요하지만, 금액류는 "있으면 좋은" 부가 필터라 우선순위를 낮췄다.

### 2-2. `user_preferred_sector` (신규)
- **완벽안**: 관심 섹터를 여러 개 + 가중치로 저장하는 정규화 테이블.
- **우리안**: 그대로 채택. 기존 `investment_profile.preferred_sector`(단일 문자열) 하나로는 테마 궁합(20%)을 제대로 못 줘서 이 테이블이 필요하다.
- **차이 없음.**

### 2-3. `recommendation_cache` (신규)
- **완벽안**: 궁합 추천 결과(점수·순위·근거 JSON)를 TTL과 함께 저장. `rec_type` 컬럼으로 'onboarding'/'long_term'을 구분하도록 이미 설계돼 있었다.
- **우리안**: 그대로 채택하되, **장투의 "개인 점수"도 여기에 저장**한다(`rec_type='long_term'`). 즉 이 테이블이 궁합 추천과 장투 추천 두 가지의 최종 결과를 모두 담는다. (왜 그런지는 2-6 `long_term_score` 설명에서 이어진다.)
- **차이**: 역할이 한 단계 넓어졌다. 완벽안의 설계(rec_type 분기)를 그대로 활용한 것이라 스키마 변경은 없다.

### 2-4. `user_liked_stock` (신규)
- **완벽안**: 사용자가 종목을 Like(=매수로 간주)한 그 시점의 PBR·궁합점수를 박제(스냅샷)한다. 장투 월 재검증에서 "PBR이 Like 때보다 ±30% 벗어났나"를 판단하는 기준점이다.
- **우리안**: 그대로 채택. 장투의 핵심 기둥이라 반드시 필요하다. 특히 **우측 스와이프(관심 등록)라는 사용자 행동이 바로 이 테이블에 기록**되므로, 우리가 행동 "로그"를 빼더라도(2-9 참고) 가장 중요한 행동은 여기에 남는다.
- **차이 없음.**

### 2-5. `holding_milestone` (신규)
- **완벽안**: 보유 30/90/180/365일 도달 시점의 지표를 스냅샷으로 남겨 "당신 90일 버텼어요, 그때보다 +12%" 같은 격려 넛지에 쓴다.
- **우리안**: 그대로 채택(장투를 데모에 넣기로 했으므로). 보유일수는 기존 `holding.first_acquired_at`로 계산 가능하다.
- **차이 없음.**

### 2-6. `long_term_score` (신규) — *구조를 바꾼 핵심 항목*
- **완벽안**: 종목별 장투 종합점수를 5개 구성요소(financial / growth / news_sentiment / technical / **user_fit**)로 저장하고, 이를 합쳐 `total_score`를 만든다. 테이블 키는 `(stock_id, calculated_date)` — 즉 **종목당 하루 한 줄**이다.
- **문제(모순)**: `user_fit_score`는 "이 종목이 이 사용자와 얼마나 잘 맞나"라서 **사용자마다 값이 다르다**. 그런데 테이블은 종목당 한 줄이라 사용자 차원이 없다. 한 줄에 사용자별 값을 넣을 수 없다. 또 `total_score`가 user_fit을 포함하면 total도 사용자별 값이 되어 같은 모순에 빠진다.
- **우리안 (결정: user_fit은 유저별 = B안)**:
  - `long_term_score`는 **종목 단위 재료만** 저장한다 → financial / growth / news / technical, 그리고 이 넷을 합친 **종목 소계**(컬럼명은 `total_score`로 두되 의미는 "종목 소계, 사용자 무관").
  - `user_fit`은 이 테이블에 **넣지 않는다.**
  - 사용자별 **최종 장투 점수**는 요청 시점에 "종목 소계 + 그 사용자의 궁합점수"를 실시간으로 섞어 계산하고, 그 결과를 **`recommendation_cache`(rec_type='long_term')** 에 저장한다.
- **이유**: 이렇게 나누면 (1) 모순이 사라지고, (2) 사용자×종목×날짜로 행이 폭발하는 걸 막고(종목 재료는 종목당 한 줄이면 충분), (3) 완벽안이 이미 만들어 둔 `recommendation_cache.rec_type='long_term'` 자리를 그대로 쓴다. 즉 완벽안의 의도와도 어긋나지 않는다.

### 2-7. `stock_dna` (신규) — *선택*
- **완벽안**: 종목의 가치/성장/안정성/변동성을 0~1로 정규화한 결과를 하루 한 번 배치로 미리 계산해 저장하는 캐시. 추천 계산은 이 테이블만 읽으면 되도록 한다.
- **우리안**: **선택 사항.** 종목 수가 약 3천 개라, 추천 요청 시 파이썬에서 즉석 정규화해도 데모는 충분히 버틴다. 또는 PostgreSQL Materialized View로 대체해도 된다. 만들면 깔끔하고, 안 만들어도 동작한다.
- **이유**: 이 테이블은 "정답을 바꾸는" 게 아니라 "속도를 높이는" 캐시다. 데모 규모에선 없어도 되니 선택으로 내렸다.

### 2-8. `long_term_score_history` (신규) — *선택*
- **완벽안**: 장투 점수의 날짜별 이력을 쌓아 "최근 30일 점수 추세(오르나 내리나)"를 보여준다.
- **우리안**: **선택 사항.** 종목 상세에 "장투 점수 추세 그래프"를 보여줄 거면 만들고, 안 보여줄 거면 생략한다.
- **이유**: 추세 카드는 있으면 멋지지만 데모 필수는 아니다.

### 2-9. `user_behavior_log` + `user_investment_pattern` (신규) — *제외 (행동 학습)*
- **완벽안**: 사용자의 모든 행동(조회/클릭/스와이프)을 로그로 쌓고(`user_behavior_log`, 월별 파티셔닝), 이를 집계해 평균 보유기간·손절비율·추매비율·선호섹터·행동기반 성향 재추정(`user_investment_pattern`)을 만든다. "말이 아닌 행동으로 성향을 학습"하는 고급 기능이다.
- **우리안**: **둘 다 만들지 않는다.** 테이블 자체를 생성하지 않고, ERD 다이어그램에는 점선으로 "행동 학습: 확장 예정"이라고만 표기한다.
- **이유**:
  1. 데모는 신규 유저라 로그가 비어 있다 → 학습 결과가 빈약해 보여줄 게 없다.
  2. 행동을 모으려면 프론트엔드에 이벤트 수집까지 붙여야 해서, 장투 기능 중 가장 비용이 크다.
  3. 빈 테이블을 만들어 두는 건 오히려 손해다 — 죽은 스키마가 ERD에 남아 혼란스럽고, `user_behavior_log`는 월별 파티션이라 매달 다음 파티션을 안 만들면 INSERT 에러가 난다. "안 쓸 거면 안 만든다"가 깔끔하다(나중에 행동 학습을 실제로 할 때 그때 모델+마이그레이션을 추가하면 된다).
- **빼도 장투가 안 깨지는 이유**: 재검증(🟢🟡🔴)은 `stock_indicator`+`financial_summary`+`user_liked_stock`만으로 돌아가고(행동 로그와 무관), 선호 섹터는 행동 학습 대신 온보딩의 `user_preferred_sector`로 대체하며, 성향은 행동 재추정 대신 온보딩 설문값을 그대로 쓴다.
- **주의 하나**: 좌측 스와이프(패스)를 로그로 안 남기면 "이미 패스한 카드가 다시 뜨는" 문제가 생길 수 있다. 데모에서는 프론트엔드가 한 세션 안에서 이미 본 카드를 덱에서 빼는 방식으로 처리하면 충분하다(세션을 넘겨서까지 기억할 필요는 없다고 본다).

### 2-10. `stocks_stocknews` / `stocks_newsrelatedstock` (기존 → 컬럼 추가) — *뒤로 미룸*
- **완벽안**: 뉴스 본문 요약·감성점수(sentiment)·관련도(relevance) 컬럼을 추가해, 종목별 뉴스 분위기를 점수화한다.
- **우리안**: **뉴스 파이프라인을 실제로 붙일 때 추가**한다. 그전까지 장투 점수의 뉴스 항목은 **50점(중립)** 으로 둔다.
- **이유**: 장투 종합점수는 뉴스 점수가 50으로 고정돼 있어도 계산이 돌아간다. 뉴스 수집·감성분석은 별도의 큰 작업이라, 장투 기둥을 먼저 세우고 뉴스는 나중에 얹는 게 안전하다.

### 2-11. `SharedPortfolio` / `SharedPortfolioItem` (기존) — *제외 (포폴 공유)*
- **완벽안**: 커뮤니티의 포트폴리오 공유 기능에 사용.
- **우리안**: 포트폴리오 공유 기능을 데모에서 빼기로 했으므로 **API를 만들지 않는다.** 단, 테이블 자체는 이미 마이그레이션돼 있으니 **굳이 삭제하지 않고 그냥 미사용으로 둔다**(삭제하면 불필요한 마이그레이션만 생긴다). 커뮤니티 게시글의 'PF(포트폴리오)' 타입도 쓰지 않는다.
- **이유**: surgical하게, 안 쓰는 것은 건드리지 않는다. 홈 화면의 "내 자산 배분 차트"는 본인 `Holding` 기반이라 이 결정의 영향을 받지 않는다.

## 3. 산식 상세 — 완벽안이 비워둔 것을 우리가 채움

완벽안은 "이 점수는 이런 컬럼에서 나온다"까지만 적고, **정확한 계산식은 비워두거나 예시만** 남긴 곳이 많았다. 데모를 돌리려면 숫자가 필요해서 아래처럼 확정했다. (전부 주린이 서비스 + 데모 기준의 단순한 식이다.)

### 3-1. Stock DNA 정규화 — 방식: **백분위(percentile)**, 하루 한 번 배치
완벽안은 "min-max 또는 분위수"라고만 적어 모호했다. 우리는 **백분위**로 정한다. 활성 종목 전체 중에서 그 종목이 몇 %에 위치하는지를 0~1로 환산하는 방식이다. min-max보다 이상치(PBR 음수, 극단적 beta)에 강하고 항상 0~1로 고르게 퍼진다.

```
volatility   = pct(beta)              # 변동성
value_score  = pct(1 / PBR)           # 저평가 (PBR이 0 이하면 0점)
growth_score = pct(net_profit_yoy)    # 성장성 (순이익 전년대비 증가율)
stability    = pct(1 / beta)          # 안정성
```

### 3-2. 궁합 점수 (온보딩 추천) → `recommendation_cache(rec_type='onboarding')`
완벽안의 5요소 가중치(35/20/15/20/10)는 그대로 쓴다. 다만 **리스크 궁합 공식에 스케일 버그**가 있어 고쳤다.

```
risk_match  (35%) = 1 - |(risk_tolerance - 1)/4 - volatility|
term_match  (20%) = term>=4 → (stability+value)/2
                    term==3 → (stability+value+volatility)/3
                    term<=2 → volatility
exp_match   (15%) = exp<=2 → stability
                    exp==3 → (stability+growth)/2
                    exp>=4 → (growth+volatility)/2
sector_match(20%) = 관심섹터면 weight, 무관심이면 0.5, 비관심이면 0
style_match (10%) = (value + growth)/2

match_score = (risk*0.35 + term*0.20 + exp*0.15 + sector*0.20 + style*0.10) × 100
```

- **리스크 공식 픽스 설명**: 완벽안은 `1 - |risk_tolerance/2.5 - volatility|`였는데, 이건 volatility가 "정규화 안 한 원래 beta(0~2)"일 때나 맞는 식이다. 우리는 volatility를 0~1 백분위로 쓰기로 했으니, 사용자 성향도 0~1로 맞춰야 한다. 그래서 `(risk_tolerance - 1)/4`로 1~5를 0~1로 환산해 둘을 같은 자 위에서 비교한다. (다른 요소들은 이미 0~1짜리 stability/value/volatility를 섞어 쓰므로 volatility도 0~1이어야 앞뒤가 맞는다.)
- **관심섹터 weight**: 1순위 1.0 / 2순위 0.6 / 3순위 0.3 (4순위 이하는 받지 않음).

### 3-3. 장투 종합점수 → `long_term_score`(종목) + `recommendation_cache`(개인)
> ⚠️ **갱신(2026-06-10):** 아래는 본래 technical/news를 포함한 초안이었으나, 최종 결정은
> [`장투점수_산정로직.md`](./장투점수_산정로직.md)로 **technical·news를 빼고 재무·성장·궁합 3축**으로 확정됐다.
> 코드(`recommend/scoring.py`)도 이 3축을 따른다. 아래 식을 그에 맞게 정정한다.

```
financial_score = 재무 4~5지표 0~100 평균   # 부채↓·유동↑·마진↑·ROE↑
growth_score    = 성장 3지표 0~100 평균      # 매출/영업이익/순이익 YoY (0%→50, ±30%→0/100)
# technical_score / news_score 는 사용 안 함 (화면엔 관련 기사만, 점수 미반영)

# 종목 단위 (long_term_score.total_score 에 저장) — 사용자 무관
종목 소계 = 재무·성장 가중평균 (재무:성장 = 0.30:0.40 → (W_F+W_G)로 정규화해 0~100)

# 사용자 단위 (recommendation_cache.match_score 에 저장, 요청 시 실시간)
개인 최종 = 종목소계×0.7 + 궁합점수×0.3
         = 재무×0.30 + 성장×0.40 + 궁합×0.30   (소계×0.7 펼치면 원비중 복원)
```

- **가중치 근거**: 장투는 펀더멘털이 주축이라 재무30+성장40으로 65%가 아닌 **70%**를 펀더멘털에 주고(성장 비중 최대 — 장기 관점), 나머지 30%를 개인 궁합으로 얹는다. 뉴스·기술은 점수에 넣지 않는다(데모 범위 + 변별력 우선). 합산 구조는 `scoring.W_MATCH/W_FINANCIAL/W_GROWTH`에서 한 곳으로 관리한다.

### 3-4. 장투 월 재검증 → `user_liked_stock.last_review_status`
완벽안의 4지표를 그대로 쓴다. 기존 컬럼만으로 계산되므로 추가 컬럼이 필요 없다.

```
위반수 = (ROE < 10) + (부채비율 > 200) + (순이익증가율 <= 0) + (|현재PBR - Like시점PBR| / Like시점PBR > 0.30)

위반 0개 → 🟢 GREEN  ("아직 좋은 파트너예요")
위반 1~2개 → 🟡 YELLOW ("지표 하나가 꺾였어요")
위반 3~4개 → 🔴 RED    ("처음 추천 이유가 흔들려요")
```

(EPS 증가율 컬럼이 따로 없어 `net_profit_yoy`를 대용으로 쓴다 — 완벽안과 동일한 가정.)

### 3-5. 행동 학습 산식 — *우리안에선 빠짐*
`behavior_inferred`(행동 기반 성향 재추정), 손절비율·추매비율 같은 행동 집계 산식은 2-9에서 행동 학습 자체를 뺐으므로 함께 빠진다. 데모에선 온보딩 설문값을 성향으로 그대로 쓴다.

## 5. 딱 하나 남은 입력 — 온보딩 문항지

5벡터(risk_tolerance 등)는 "온보딩 문항 응답 → 1~5 점수"로 만든다. 한 컬럼이 문항 하나에서 나오는 게 아니라 **여러 문항을 묶어서** 나온다(예: investment_term은 투자목적+기간+방식 3문항의 평균). 이 매핑을 확정하려면 **실제 설문 문항지 + 보기별 점수**가 필요하다.

- 구조: 각 문항 보기마다 1~5점 부여 → 해당 벡터에 매핑(겹치면 평균).
- 결정 필요: `loss_aversion`은 현재 어느 문항도 배정돼 있지 않다. (전용 문항 추가 / 손실대응 문항을 둘로 분할 / 데모에선 미사용 중 택1.)

문항지가 정해지면 이 표만 채우면 추천 입력이 완성된다.
