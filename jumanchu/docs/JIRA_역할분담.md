# 주만추 3인 역할 분담

> 광주 1반 6조 / 강재민(BE) + 정율(추천) + 송호영(FE)

---

## 1. 큰 그림 — 누가 무엇을 소유하는가

| 영역 | 책임자 | 무엇을 소유하나 |
|---|---|---|
| **백엔드 (BE)** | 강재민 | Django 코드 전부 — 모델/뷰/URL/마이그레이션, 외부 API 연동(주식·DART), 추천 함수를 호출해 REST API로 노출, CI/CD, 인프라 |
| **추천 (Algo)** | 정율 | 추천 도메인 기획 + 순수 Python 알고리즘 함수만. 입력 데이터를 받아 추천 결과를 반환. Django 코드는 짜지 않음 |
| **프론트엔드 (FE)** | 송호영 | Vue.js 코드 전부 — 컴포넌트/라우터/Pinia 스토어, API 호출, 스와이프 UI, 디자인 시스템 |

### 한 줄 요약
- BE는 **"껍데기"**: 모든 입출구를 만든다 (API, DB, 외부 연동).
- Algo는 **"두뇌"**: 추천이 무엇을 어떻게 추천할지 기획하고, 그 함수를 만든다.
- FE는 **"얼굴"**: 사용자가 보는 모든 화면을 만든다.

## 3. 모호한 경계 — 자주 헷갈리는 케이스

| 작업 | 누구? | 이유 |
|---|---|---|
| 뉴스 크롤링/저장 | **BE** | 외부 API 연동·DB 저장 영역 |

| 종목 위험성향 분류 (베타/MDD 계산) | **Algo** | 자체 계산, 추천 입력으로 활용 |

| 일기 데이터를 추천에 어떤 형식으로 넣을지 | **Algo가 정의** | 모델 입력 스키마는 Algo가 정한다 |
| 일기 데이터를 실제로 수집·저장 | **BE** | DB·CRUD 영역 |
| 투자 MBTI "당신은 ENFP형 투자자" 결정 로직 | **Algo** | 분류 알고리즘 |

| 추천 API URL 명세 (예: `GET /api/v1/recommend/news`) | **BE** | API는 BE 책임 |
| Algo 함수의 입출력 시그니처 정의 | **BE + Algo 함께** | 협업 인터페이스 |

## 4. BE ↔ Algo 인터페이스 — 가장 중요한 협업 지점

**원칙**: Algo는 함수/클래스만 만든다. BE는 그걸 import해서 뷰에서 호출한다.

### 예시: 트렌딩 뉴스 기반 추천

```python
# Algo 담당이 작성: backend/recommend/news_based.py
def recommend_by_trending_news(user_id: int, limit: int = 10) -> list[StockRecommendation]:
    """
    사용자 ID와 현재 트렌딩 뉴스를 기반으로 관련 종목을 추천.

    Returns:
        StockRecommendation 객체 리스트. 각 객체는 {ticker, score, reason}.
    """
    ...

# BE 담당이 작성: backend/recommend/views.py
class TrendingRecommendView(APIView):
    def get(self, request):
        recs = recommend_by_trending_news(request.user.id, limit=10)
        return Response([rec.to_dict() for rec in recs])
```

### 인터페이스 합의 체크리스트

새 추천 기능을 시작하기 전 BE와 Algo가 같이 정해야 할 것:
- [ ] 함수 이름과 파라미터 (`user_id`, `limit`, `since` 등)
- [ ] 반환 타입 (리스트? 딕셔너리? 데이터클래스?)
- [ ] 입력으로 어떤 DB 데이터에 접근할 수 있는지 (Algo가 직접 ORM 쓸지, BE가 미리 가공해서 전달할지)
- [ ] 오류 처리 (추천할 데이터가 없을 때 빈 리스트? 예외?)
- [ ] 성능 기대치 (응답 시간, 캐싱 필요 여부)

위 합의는 Jira 이슈 본문이나 Notion 페이지에 적어두면 됩니다.

> 💡 **Algo 의존성 완화 팁**: 정율이 첫 PR로 **더미(stub) 함수**를 머지하면(랜덤 종목 반환), BE/FE는 그걸로 먼저 통합 시작 가능. 진짜 알고리즘은 나중에 갈아끼우기.

## 5. FE ↔ BE 인터페이스

**원칙**: API 명세는 BE가 정하고 FE는 그걸 호출한다.

- BE는 Django REST Framework로 엔드포인트를 만들 때 **OpenAPI/Swagger 문서**를 자동 생성하거나, 간단히 `docs/API_SPEC.md`에 표로 정리.
- FE는 그 명세를 보고 axios 호출 코드를 작성.
- 명세 변경 시 BE가 먼저 알리고, FE 작업이 깨지지 않게 deprecation 기간을 둠.

## 6. Jira에서 분담 표시하는 방법

각 이슈에 다음을 적용하면 보드에서 누구 일인지 한눈에 보입니다.

### 라벨 (담당 영역)
- `backend` — BE 작업 (강재민)
- `algo` — 추천 알고리즘 작업 (정율)
- `frontend` — FE 작업 (송호영)

> 한 이슈가 BE+FE 양쪽 일이라면 Story로 두고 sub-task로 나눠서 sub-task별로 라벨 단일 지정.

### 담당자 (Assignee)
이슈 상세 패널에서 담당자를 지정. 보드에서 담당자 아바타로 필터링 가능.

### 보드 필터 활용
보드 우측 상단 사람 아이콘 → 자기 아바타만 클릭하면 "내 카드"만 보입니다.

## 7. 협업 원칙 3가지

1. **인터페이스 먼저 합의**. 함수 시그니처/API 명세를 코드 작성 전에 정한다. 나중에 바꾸면 양쪽 다 고쳐야 한다.
2. **모르면 코멘트로 묻는다**. Jira 이슈 코멘트나 슬랙에. 머릿속으로 가정해서 짜고 나중에 충돌하지 않게.
3. **자기 영역 PR은 다른 트랙 한 명이 리뷰**. BE PR은 Algo나 FE가 한 번 훑기. 코드 리뷰로 도메인 지식이 전파된다.
